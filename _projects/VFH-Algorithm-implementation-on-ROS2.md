What is VFH ?
VFH or Vector Field Histogram is an algorithm used as **local planners** for object avoidance, implemented with autonomous robots. It relies on a **grid** that acts as a **world model** generated by a two dimensional histogram and updated continuously. To calculate the proper velocities that we need to feed our system, VFH uses a two-stage data reduction process, in the first stage the histogram is reduced to a **polar histogram** that is centered around the robot's momentary location, each sector, which is an equivalent of a range of angles in the polar histogram, contains a value that represents the obstacle density in the direction of the robot. This algorithm was published in 1991 by Johann Borenstein and Yoran Koren, both professors at the University of Michigan. It is the successor of the VFF method that was developed by a group within the same university as the authors of VFH algorithm [1].

# VFH Evolution:

VFH passed through multiple stages of development after its first publication in 1991.
* In 1998, the same author, "Johann Borenstein", proposed what is well known as VFH+ which proposed a more reliable solution for sensor noise, latency and low sampling rate, by using hysteresis to catch the slipping values [2].
* VFH Star: In 2000, Ulrich and Borenstein proposed "VFH star", which is an enhanced version of VFH and VFH+ that uses an additional search and verification algorithm to validate the goal [3].
These are just some of the proposed enhancements of VFH algorithm; there are many research papers that proposed the usage of VFH for different types of autonomous robots like UAVs [4].

# Implementation

This tutorial is for the sake of understanding of how robots move and interact with their environment by using raw data coming from sensors. To implement the VFH algorithm we will use ROS2 as development environment and GZ Fortress as a physics simulation environment. From the previously mentioned research papers [2][3], the source of data is coming from ultrasound sensors. Here in our case we will use a 2D LiDAR  [4] which is a laser-based sensor that emits light and measures the time it took to bounce back to define distance. All the data coming from our actuators and sensors is generated by our physics simulation model GZ, and then we bridge the raw data to ROS2.

1. LiDAR Parametrization:
Every LiDAR sweep occurs between a range min and max, with a specific angle between beams called the angle increment. To facilitate calculations, we set angle increment = sector size = 5°. The total number of samples is set to 32, which means that we have a 2D histogram that measures the frequency of 32 sectors. The whole array of data coming from our LiDAR needs to be treated, all **NaN** and **inf** values need to be present in our calculation since we choose increment angle = sector size, all the distances measured can't be dropped. We will see later how we are going to handle **NaN** and **inf** values.
**NaN** values can be due to many factors related to our hardware, synchronization issues or an invalid value. In simulation it is relatively rare we find **NaN** values. **Inf** means that our beam never bounced back.
2. **Robot:**
Oppressor mk2 is the robot of our choice to simulate the algorithm. It is equipped with an RGB Camera and a LiDAR. The control of the wheels is handled with ros2\_control using a differential drive controller.
3. **Algorithm:**
The main goal of the development of this algorithm on oppressor mk2 is to enhance the line follower project [5] by presenting a solution for the objects that come across our robot's path.
* **Sensor Reading:** First, we need to create a subscription to read from our bridged topic called "/scan" of message type **"sensor\_msgs/msg/LaserScan"**.
* **NaN and inf values filtration:**  all the distances stored inside **ranges** need to be filtered for any distance that holds a NaN or an inf value, and we set its distance and magnitude to 0.
* **Distances processing:**  if we read any value other than **NaN** and **inf**, we proceed to calculate the equivalent angle (in radians), sector and magnitude.
$$
Magnitude (K) = A - B\times D \tag{1}
$$
**A** and **B** are constants defined based on our sensor max range.
**D** is the distance measured by the LiDAR.
* After calculating all necessary values, we need to decide which sector is valid, and we proceed to filter our magnitudes by applying a threshold. Based on the research paper proposed by Ulrich and Borenstein [2], which is an improved version of VFH called VFH+. They stated that due to the long sampling time of their ultrasound sensor and noise, they proposed a solution by applying a hysteresis-based filter where they set two thresholds and any sector between these two thresholds, its state depends on the state of the previous sector [2]. In our case, we will keep it simple right now by applying a simple threshold to filter our sectors. After filtering our sectors, we end up with an array (vector) that holds the state of 32 sectors we have (true = open sector, false = closed sector), all the states are indexed, and based on their index and state we define whether this sector is safe for steering.
* **Extending closed sectors:** here comes one of the most important steps that we need for our algorithm and it is angle enlargement. This angle will give our algorithm more privilege to  access our environment and build a better perception. This angle is calculated based on our **robot dimensions** and a **safety margin** that we set. Based on the angle we calculated, we proceeded to extend sectors around the obstacle [2]. All blocked sectors need to be updated based on the number of sectors. Figure 1 shows how the angle is calculated based on robot radius and safety margin (if set).
$$
\\alpha = asin(\frac{r}{d}) \tag{2}
$$**r**  is the sum of robot radius plus safety margin if there is any.
**d**  is the distance between the safety margin and the obstacle.
* Finally: We proceed to store valid pairs of sector indexes, which set the start and end of an open sector.

## Results:
For simulation, we have created a custom ros2 message that stores all necessary calculated values we need for our polar histogram and polar plot **Figure 3**.
```
float32[] angles
float32[] distances 
int32[] sectors
float64[] magnitude
bool[] state
int32[] valid
float32 treshold
```
The algorithm is tested in a maze map that can be found here [5]. The steering of the robot is simple, our robot needs to move forward aiming at sector 0 which is the equivalent of 0°, now if sector 0 is among valid pairs the robot will move forward, if sector 0 is blocked, then our algorithm will proceed to calculate the shortest distance of the valid pairs of sectors, once the sector with the shortest distance is found, the steering towards the nearest free sector starts. Figure 2 shows how our robot navigates through the maze without interfering with walls. The map has been generated by Nav2 stack [6] and later used for visualizing the path generated by our algorithm. (Circles in purple represent position, in green filtered odometry)

From **Figure 3**, we can see that the polar histogram identifies the valid sectors and the blocked ones (exceeding our threshold), we can clearly see that (11, 18) and (45, 63) are valid pairs and we can navigate through them and the rest are blocked sectors. The logic behind the valid pairs is simple, the robot will navigate to the sector with the shortest distance. As stated before, we have tested our sensor with two different configurations, 
* In the first configuration, with a FOV of 160°, the robot showed expected behaviour; in some cases, the robot found itself trapped in a dead end where all the sectors are blocked.
* In the second configuration, we used a sensor with full FOV 360°, sector size 5°, and number of samples 72. This configuration showed the best performance. Figure 2 shows the robot moving without interfering with objects and walls.
In the case of a sudden object spawning in front of the robot, the algorithm interacts effectively and avoids it by navigating away from it.
This algorithm is very effective as a local planner and offers robot perception by setting an enlargement angle. Integrating VFH with a cost map will make it a perfect algorithm for navigation between a start point and a goal point with the capability of avoiding obstacles.
