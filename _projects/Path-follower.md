Three-term controller is among the most used controllers. It is a feedback-based control loop mechanism, and it is widely used with physical and non-physical systems. Thanks to its closed-loop architecture, the controller automatically compares the set point (desired value) with the actual value our system is outputting [1].
In this project, we will implement this controller with our Oppressor MK3 robot to navigate through an open environment using a lead, which in our case is a black line drawn on the floor, along with a VFH as a local planner to avoid objects. These two algorithms are orchestrated by a Behaviour Tree that sets up when and how every action is going to be executed.

## Implementation:
We use ROS2 as a framework and Gazebo Fortress (GZ) as a simulator. Our simulated robot "oppressor mk3" is equipped with a camera and a LiDAR. The data generated by Gazebo is sent to ROS2 through the ros_gz_bridge, and each node subscribes to the topic it needs. As a map we are using a simple map drawn using Paint, imported into Gazebo, with a path to follow and 3 obstacles spread along it. We will start with the LiDAR. The bridged topic called /scan publishes a message of type ‘sensor_msgs/msg/LaserScan’, and from this message type we can get a lot of information, starting with angle_min and angle_max, angle_increment, and the distances measured from the reflected laser beams. The /scan topic is crucial since our local planner subscribes to it, and from its messages our robot can build a perception about its environment and avoid obstacles. After we pass the information received from our LiDAR, all the information is treated by the VFH algorithm node, which calculates an angular velocity that we need for steering the robot away from the obstacle. We publish its value as a topic called “/vfh/cmd_vel” of message type “geometry_msgs/msg/TwistStamped” Figure 1.

In parallel we receive every frame captured by the camera, published as a message of type sensor_msgs/msg/Image. Then the frame is fed into our image processing node, which passes every captured frame through a series of transformations. First we start by filtering the image, then we change its colors to grayscale. This step is very important later when we start calculating our moments. Then we proceed to selecting our region of interest (ROI). In our case, the camera placed on the front of the robot is tilted around the pitch axis, focusing only on the bottom part to avoid disturbance and noise coming from the shadows. For the ROI we are interested in the bottom third of our frame. After selecting the ROI we proceed to measure how far our measured moments are from the x-axis center. The logic here is to keep the difference between the moments and the x-axis center equal to 0. This is what we call the error, which will then be published as a Float64 message. The calculated error is then fed to our PID controller, which will proceed to calculate the desired angular velocity we need to steer our robot to the center of the image frame. The calculated angular velocity is then published as a topic named /controller/cmd_vel of type geometry_msgs/msg/TwistStamped. The published topics that hold the angular velocities calculated by our LocalPlanner node and Controller nodes need to be organized in a way that we know which one we need to feed to our differential drive controller. That's why we are using behavior trees Figure 2, which are the main actor here for orchestrating and selecting which velocity needs to be published based on the condition of whether there is an object ahead of our robot Figure 1.

Figure 2 shows the tree that controls which velocity command we are publishing to our driver. For this purpose we are using the BehaviorTree framework from Auryn Robotics [2], and we rely on their software Groot2 to visualize live monitoring of our tree. Every tree needs a tick signal, which is generated by the tree executor (our main program) and sent to the root node, and for every tick signal the set of nodes is executed based on the returned value, whether it is SUCCESS, FAILURE or RUNNING. Then we have a main root node of type Fallback, which means that this node will have a SUCCESS status only when one of the child nodes has a SUCCESS status (if all nodes return FAILURE status it returns FAILURE). Then we have two child nodes, the first one is of type sequence and the second one is the action PathFollowing. A sequence node executes children nodes from left to right and returns SUCCESS when all children nodes have a SUCCESS status. If one child fails, the parent node fails. So if we interpret what is in Figure 2, we see that we have 3 nodes, 1 condition and 2 actions. When we start executing our root node the tick passes through nodes from left to right, and the first node that receives the tick is the sequence node, which then executes IsObstacleDetected. This node is a conditional node that checks a boolean value computed from the /scan data and based on it returns SUCCESS only when an obstacle is present within the safety range in front of the robot. If nothing is present there it will return FAILURE and the sequence node's status is FAILURE, which will lead to executing the action PathFollowing. Now what happens if IsObstacleDetected returns SUCCESS? It will lead to executing our next action, which is AvoidObstacle, which itself will only publish the received angular velocity from the '/vfh/cmd_vel' topic to our diff drive controller. Once the message is published it will return SUCCESS (in our case it always returns SUCCESS, there is no case where it will return any other value than SUCCESS, we could set it to return RUNNING). When the sequence node has SUCCEEDED, the Fallback node also SUCCEEDS and the tick ends, so PathFollowing is not executed. When the sequence node has FAILED, we pass to the PathFollowing action node, which has a simple role: it publishes the received angular velocity from the controller so we steer the robot and set it to follow the path. The tree is ticked again every cycle, so the robot reacts to any new situation on the next tick.
